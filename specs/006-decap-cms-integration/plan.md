# Implementation Plan: Decap CMS Integration

**Branch**: `006-decap-cms-integration` | **Date**: 2026-05-25 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/006-decap-cms-integration/spec.md`

## Summary

This plan outlines the architecture, data structures, validation pipelines, and routing needed to integrate Decap CMS for editing services, projects, and media files. The technical approach involves:
- Setting up static CMS admin entry points (`/admin/`) with custom live preview templates (iframe-based render templates).
- Enabling Decap CMS `editorial_workflow` for tracking draft and review states in production, with roles, branch protection, and Netlify identity triggers.
- Enforcing strict slug generation (autogenerated from title, readonly after creation, unique validation) to protect URL mapping.
- Utilizing a unified translation linking system using identical filenames in English and Arabic locale content collections.
- Defining fallback UX behavior: Keep language switcher active. If translation is missing in the target locale, fallback to show default locale content inside the target layout alongside a localized warning banner.
- Filtering draft routes in production builds (`import.meta.env.PROD === true`), but allowing them to generate on preview/staging deploy environments.
- Mapping full SEO attributes, dynamic JSON-LD structured schemas, robots, and sitemap settings to enable search optimization.
- Organizing taxonomy schemas containing reusable categories and tags.
- Reducing config duplication in `config.yml` using YAML anchors (`&`) and aliases (`*`).
- Hooking image uploads into Astro's native build-time Sharp image pipeline for automated WebP conversion and lazy-loading.
- Creating a pre-migration backup structure in `.backup/` with a rollback recover policy.

## Technical Context

**Language/Version**: TypeScript 5.x / Node.js 18+

**Primary Dependencies**: Astro (latest), Tailwind CSS, Sharp, `@astrojs/sitemap`, decap-cms-app (loaded via CDN inside `/admin/`)

**Storage**: Astro Content Collections (markdown files under `src/content/`)

**Testing**: Playwright (E2E), Vitest (Unit), `astro check`

**Target Platform**: Static Host (Vercel/Netlify)

**Project Type**: Localized Web Application

**Performance Goals**: Lighthouse performance score >= 90, SEO score 100, CLS = 0

**Constraints**: No GSAP, no global client runtimes (CMS is restricted to `/admin/`), Tailwind logical properties only, zero unnecessary hydration.

**Scale/Scope**: Multilingual CMS dashboard for two core collections (services & projects) and media uploads, with future compatibility for testimonials, blog posts, and category structures.

```text
├── assets/
│   └── images/
│       └── uploads/     # Target folder for CMS uploaded images (for Astro optimization)
├── content/
│   ├── config.ts        # Astro content schemas (services, projects schemas with Zod validation)
│   ├── services/        # Existing services collection (updating frontmatter fields)
│   └── projects/        # New projects markdown files (en & ar, mapped by identical filename slugs)
└── pages/
    └── [lang]/
        └── projects/
            ├── .backup/      # Temporary backup directory for hardcoded page rollbacks
            ├── [slug].astro  # New dynamic route replacing old static pages
            └── (deleted coffee-shop.astro, marketing-roi.astro, oxygen-gym.astro)
```

**Structure Decision**: Place the CMS admin interface in `public/admin/` to expose `/admin/` in the build output, keep CMS uploads in `src/assets/images/uploads/` to enable native Astro `<Image />` compilation and WebP conversions, and group all markdown files under `src/content/` mapped by identical filenames to support translation linking.
